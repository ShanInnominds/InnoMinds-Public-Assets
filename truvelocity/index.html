Why it matters

AI agents fail in ways ordinary tests never see

An agent can sound right and still be wrong. The failures that cost money and trust happen between what it says and what it does.

  • Says it's done when it isn'tThe reply reports a payment or change that never reached the system of record.
  • Does the wrong thingCalls a tool it shouldn't, acts for the wrong customer, or skips an approval.
  • Leaks or follows an attackerShares another person's data, or obeys an instruction hidden in a pasted note.
  • Works once, fails on repeatPasses today's demo, then answers the same question differently tomorrow.
How it works

Every turn checked at five points, every claim checked against the systems

Each question in a test catalog states what must be true. TruVelocity follows the turn through five checkpoints and reports the first one that went wrong, so a failure points straight at its cause.

1GoalDid it understand what was asked?
2PlanDid it choose the right steps and approvals?
3ActionDid it call the right tools, with the right arguments?
4End stateDid the right data change, and nothing else?
5OutputIs the reply true, complete and safe?

Cross-checks between the stages catch what each one alone misses: a reply claiming success for a write that failed, data that changed without a call, an approval that was declined but acted on anyway.

Capabilities

Everything a release decision needs, in one framework

Drive any agent

Chat over WebSocket or HTTP, task agents over HTTP, OpenAI-compatible endpoints, and agents behind Azure Service Bus or Kafka. Chat assistants, task agents and multi-agent orchestrations, built with LangGraph, the OpenAI Agents SDK or your own code.

Independent evidence

A recording MCP proxy sees every tool call (and injects faults on demand), an OpenTelemetry GenAI receiver reads traces, an agent-to-agent tap records hand-offs, and state readers for SQL, REST, git and files show what really changed. The agent's own word is never the only evidence.

Judged the same way every time

Rule-based checks and an LLM rubric judge, the judge calibrated against labelled cases (Cohen's kappa) before you trust it.

Reliability, not one lucky run

Every question asked in many wordings and repeated; pass^k, 95% Wilson intervals and flaky cases show whether a pass will hold in production.

Ready-made test packs

Privacy, prompt injection, payments and approvals, unsafe writes, identity hand-offs, conversation handling, answers and boundaries, tone and policy. Add one to a catalog with one command.

Suites and cost up front

Tag questions as sanity, smoke, regression, security and more; run one suite; see the estimated time and tokens before you start.

Release gate and reports

A release gate per capability and severity, an execution report for stakeholders, an engineering report, JUnit for CI, defect lists, run-to-run comparison and a consolidated view across runs.

Built into delivery

One command writes a GitHub Actions or Azure Pipelines job that runs and gates. Runs are shared through a folder, S3, Azure Blob Storage or a SQL database, with a portfolio across projects.

Works with AI assistants

An MCP server offers every command as a tool, so an AI coding assistant can run, read and gate tests for you.
